# PS-14 — Check #30: Fraud Alert Quality & Investigator Workflow Audit

**INVESTIGATOR WORKFLOW VERDICT: FAIL**

The audit exercised the real verification-service endpoints (FastAPI TestClient)
against sandbox copies of risk.db / verify.db / audit.db with the real `.env`
secrets — the live DBs were untouched. Evidence: `reports/alert_quality_audit.json`
(generated by `scripts/alert_quality_audit.py`, 4 s).

**Headline finding: the investigator case workflow cannot create a case.** Every
`POST /investigator/cases` returns **500** (`NOT NULL constraint failed:
investigator_cases.score_id`) because the endpoint never supplies `score_id`,
which the schema declares NOT NULL with no default. The workflow has never been
exercised against the live schema — the code-level SELECT-then-INSERT dedup check
and the `case_created` audit event are both unreachable, and no caller anywhere in
`src/` auto-creates cases from high-risk scores despite the endpoint's own
docstring claiming it is "called automatically".

## 2. Alert prioritization — PASS (ranking consistent; source is model-derived)

Priority = `risk_score × confidence weight` where confidence maps from the model's
ml_score uncertainty (high 1.0 / medium 1.2 / **low 1.5** — uncertain cases float
up). The API sorts strictly descending by priority: measured [135, 96, 90, 70, 60,
40]. Server-side ordering, no UI override of risk ranking.

## 3. Decision traceability — FAIL for the workflow surfaces

| What | Retains |
| ---- | ------- |
| `risk_scores` row | event, fraud, score, band, **model_version**, ml_score, rule_score, reason_codes, degraded, scored_at |
| Audit `score_generated` | model_version, feature_version, rule_version, ml_score, odds, degraded, drift_state, reason codes |
| **Alert payload (`/alerts`)** | event, score, band, reason codes/text, scored_at — **no** model_version, feature_version, locked threshold, ml_score, feature values, explanation |
| **Investigator case payload** | case_id, fraud_id, event, status, confidence, priority, risk_score, reason codes, notes, timestamps — **no** model_version, feature_version, threshold, ml_score, feature values, explanation |

No row anywhere stores the **feature values used** for the decision or the
**locked threshold**, and no per-alert SHAP/explanation is surfaced to the
investigator. The rich trace exists in the audit chain only; the people working
alerts cannot see it.

## 4. Explainability validation — PARTIAL (exact attribution, unsafe as linear advice)

Tested on the real deployed engine with native TreeSHAP (`pred_contribs`, margin
scale):
- **Additivity verified to 7.9e-08** — sigmoid(Σcontribs + bias) == predict_proba:
  the explanation corresponds to the actual prediction on this transaction.
- **Sensitivity, up-move:** raising the top movable contributor's input moves the
  margin in the contribution's direction — consistent.
- **Sensitivity, down-move: INVERTS.** Lowering `amount_ratio` 3.0 → 1.2 raises
  the margin (4.53 → 5.35) despite a positive +1.78 contribution. Measured
  response curve is non-monotone (margin dips near ratio ~4, rises toward 1.0–1.6
  and toward ~0.2), so "lower this feature to reduce risk" is false here. SHAP
  attributes exactly but is not linear advice.
- **Top contributors are unmovable at runtime:** `mcc_n`, `has_zip`,
  `city_fraud_rate` (constant zeros/baseline in the runtime mapper, checks
  #21/#27) dominate every explanation and have no real-time input an investigator
  (or attacker) could act on.

## 5. Alert deduplication — code-level for confirm, missing at DB level for cases

- User confirm path: server-side 409 on a second confirm for the same score
  (`alert already resolved`), outcome keyed by `score_id` FK.
- Investigator case path: **no UNIQUE constraint on `investigator_cases.event_id`**
  — two rows for the same event insert cleanly (measured 1 → 2). The only guard is
  the in-code SELECT check inside the broken create endpoint. A fixed endpoint
  still needs a DB constraint or upsert before retries are safe.

## 6. Case lifecycle — PASS (transitions enforced)

Measured over the API: `NEW → REVIEWING → USER_VERIFICATION →
CONFIRMED_SUSPICIOUS → CLOSED` all 200; from CLOSED every transition → 400; from
NEW straight to CONFIRMED_SUSPICIOUS → 400. Gates come from the in-code
`CASE_TRANSITIONS` map only — no DB CHECK/trigger, so a concurrent or skip-write
bypass is possible on a non-SQLite backend (single-process correct).

## 7. Feedback loop — labels exist only from user confirmations

- Label definition is consistent: user "this was me" → `confirmed` → label 0;
  "not me" → `disputed` → label 1 (`export_feedback.py`); `resolved_at`
  timestamped.
- **Investigator verdicts never become labels**: transitions to
  CONFIRMED_SUSPICIOUS / CONFIRMED_LEGITIMATE write **no** `verification_outcome`
  row (measured: 0 outcomes after a CONFIRMED_SUSPICIOUS closure). The
  `CONFIRMED_*` terminal states are disconnected from the retraining pool.
- No path can modify historical training data (labels join DB-2 *stored* feature
  vectors at ingest time; export writes new dated snapshots only), and stored
  features predate any label — future labels cannot leak into past feature
  computation (PASS).

## Verdict

**INVESTIGATOR WORKFLOW VERDICT: FAIL.** The clean parts are real: one alert per
event with DB uniqueness, consistent server-side priority ranking derived from
model confidence, an enforced lifecycle state machine, a store that absorbs an
alert flood without drops, an exact-and-additive (if non-linear-advice) per-row
explanation capability, and audit-chain records of every transition. But the
workflow the investigators would actually use is broken end-to-end: **cases
cannot be created through the API** (schema/endpoint mismatch that no test ever
caught), nothing auto-creates cases from high-risk scores, the case and alert
surfaces are stripped of model/feature/threshold/explanation traceability, case
dedup has no DB constraint, investigator conclusions never become training
labels, and the confirmed-fraud rate among alerts is unmeasurable because no
labels exist. PS-14's alerts are generated cleanly, but they are not yet
investigable, traceable, or self-improving through the workflow that is supposed
to consume them.
