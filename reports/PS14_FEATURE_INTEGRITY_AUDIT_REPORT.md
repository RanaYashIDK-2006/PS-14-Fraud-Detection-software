# PS-14 — Check #27: Production Data & Feature Integrity Audit

**Verdict: FAIL** — the deployed lean-15 model and the offline training pipeline share
*names, order, and counts*, but not *definitions*. 13/15 features are definitional
mismatches; 6 features are structurally constant in production while varying in
training; both fraud-rate features are frozen at a constant baseline in the actual
deployed call path.

Evidence: `reports/feature_integrity_audit.json` (generated by
`scripts/feature_integrity_audit.py`, 30 s, engine loaded live from
`models/production/`, training stats over a 1,219,350-row sample of
`data/_sorted_cache/features_all.parquet`, production reference = 199 real DB-2
transaction rows mapped through the deployed mapper).

---

## 1. Schema integrity — PASS (names/order/types), with semantic caveats

Checked dynamically against the loaded artifacts: the mapper's `ALTMAN_FEATURES`
list, `models/production/manifest.json`, the deployed `RobustScaler`, and both
boosters all agree exactly on 15 feature names, in one order, with 15 inputs each
(`mapper == manifest == scaler.n_features_in_ == xgb == lgb`). Feature order is
therefore safe: the engine maps by **explicit position from one hardcoded list**,
so a reordered *input dict* cannot feed the wrong feature (verified — shuffled-key
dict maps to an identical vector). Units/scales, however, differ wildly between
train and production (see §4), and categorical *encoding* is not an issue only
because the only true categorical (MCC) is hardcoded to 0 in production.

## 2. Feature-definition matrix (the core finding)

Train definitions are from `scripts/train_altman_fullscale.py` pass 2 (L140-310)
materialized into `features_all.parquet`; production definitions are from
`map_ml_features_to_altman` (`src/risk_engine/altman_ensemble.py`). The deployed
model is the 15-feature retrain over that cache (`scripts/retrain_15feat.py`).

| Feature | Train Definition | Production Definition | Exact Match? | Evidence | Result |
| ------- | ---------------- | --------------------- | ------------ | -------- | ------ |
| `log_amt` | log1p(raw IBM dollar amount) | log1p(amount_ratio × 100) | NO | train median 3.43 vs prod corpus median 10.46 | **FAIL** |
| `amt_sq` | raw amount² | (amount_ratio × 100)² | NO | train median 1,301 vs prod corpus median 1.2×10⁹ | **FAIL** |
| `hour_cos` | cos(2π·hr/24), real hour | cos(2π·hr/24), real hour | YES | identical formula | PASS |

| `is_online` | IBM online-txn indicator | hard copy of `chip` value (new_device_flag) | NO | prod `chip` ≡ `is_online` for every row (r=1.0); train chip vs online are independent | **FAIL** |
| `mcc_n` | real MCC code, 109 unique values in sample (1,711–9,402) | **0.0 hardcoded** | NO | **structurally constant**; SHAP top driver of every decision (check #21) | **FAIL** |

| `city_fraud_rate` | per-city cumulative confirmed-fraud ratio (median 0.0, 94 K unique) | tracker rate keyed by `city_id` — **no `city_id` in call path** → baseline **0.001 every row** | NO | **structurally constant**; same self-referential label source | **FAIL** |

**Summary: 2 exact matches, 13 mismatches. 6 features are structurally constant
in production while varying in training** — verified by sweeping 600 varied legal
inputs (amount_ratio 0.02–300, all hours, flags 0/1, tenure 0–3000 d, velocity
0–60) through the real mapper: `mcc_n`, `has_zip`, `has_state`,
`merch_fraud_rate`, `city_fraud_rate`, `amt_x_mcc` never change, so they cannot
carry signal in any deployed decision. Four are constant zeros (`mcc_n`,
`has_zip`, `has_state`, `amt_x_mcc`) — features that were variable, high-signal
inputs in training are *dead in production*.

## 3. Runtime robustness probes (real engine)

| Probe | Result |
| ----- | ------ |
| Empty dict (all keys missing) | No rejection — silent defaults (amount_ratio→1.0, hour→12, chip→0, rates→0.001 …); at the HTTP boundary the 13 required `FeatureVector` fields are enforced (422), but the optional keys (velocity, entity ids) default silently **inside the mapper** |
| NaN / −inf / negative `amount_ratio` | HTTP boundary **rejects** (422, pydantic `ge=0`) |
| **+inf `amount_ratio`** | **Accepted** at the boundary; mapper replaces with 1e6 → deterministic saturated score → later caught by `_RANGE_CHECKS` (domain-shift escalation). Deterministic but not rejected at input |
| NaN `hour_of_day` / NaN `failed_auth` | Passed through the mapper as **0 after `nan_to_num`** (engine level) — silent replacement, no warning |
| Extreme amount_ratio 1e9 | Deterministic vector (large but finite); no crash |
| Empty / random entity ids | No crash; empty → baseline 0.001 rates; random → tracker lookup (baseline when window empty) |
| Wrong-typed value ("abc" in numeric slot) | **Raises** ValueError → risk engine catches → rules-only degraded decision (fails safe, never a wrong silent score) |
| Reordered input dict | Identical vector (mapping by key name) — **ordering safe** |
| Determinism | map ×5 identical; engine.predict ×3 identical; fresh engine instance → identical score; scaler.transform identical — **fully deterministic** |

(train mcc 1,711–9,402). The model is extrapolating on production input.

## 5. Scaling / encoding — PASS on fit-scope, FAIL on effective parity

`RobustScaler` is fitted **only on the training split** (80% random split of the
cache, `retrain_15feat.py` L93-99) and reused unchanged at test and inference —
verified: transform is the only operation at runtime, no refit, deterministic.
So the letter of "preprocessing fitted on training only" holds. But because the
*mapper's output values* are definitionally different from the training columns
(§2/§4), the scaler centers/scales production vectors at values the scaler never
saw — the fit is on a different distribution than the one it transforms.

## 6. Historical-feature correctness — FAIL

- **Offline (`merch_fraud_rate`/`city_fraud_rate`/`merch_tx_count`):** computed as
  cumulative running state in **file order** (`train_altman_fullscale.py` L252-298),
  not anchored to row timestamps. Check #24 independently quantified the
  consequence: 66.8% of merchant-rate rows change value under strict chronological
  replay (max |Δ| = 1.0 — early-dated rows absorbing later-dated fraud), and a
  chronological rescore drops AUC 0.9952 → 0.9229 with FPR exploding to 50.1% at the
  locked operating point. **Future records can and do affect a "historical" train
  feature.**
- **Label availability timing offline: UNVERIFIED** — the dataset has no
  fraud-confirmation timestamp, so when an offline label became available to the
  expanding window cannot be proven.
- **Production:** the tracker is a 100-event in-memory deque (min 5 events,
  baseline 0.001), recording events *after* they are scored (no future data —
  PASS) — but its labels come from `risk_score ≥ 70` (`_record_entity_rates`),
  i.e., **the model's own decisions**, not confirmed fraud; state is lost on
  restart and re-seeded from the top-5000 DB-2 rows; and, decisively, **the
  deployed call path (privacy ingest → `/internal/evaluate`) sends no entity ids**,
  so both features are frozen at baseline 0.001 on every transaction.

## 7. Verdict

| Check | Result |
| ----- | ------ |
| Schema names / order / count | PASS |
| Feature definitions identical | **FAIL** (13/15) |
| Production features carry training signal | **FAIL** (6 features structurally constant in prod, 4 of them frozen zeros) |
| Fraud-rate features reproducible at real time | **FAIL** (frozen baseline in the call path; offline definitions contaminated by file order — check #24) |
| Scaling fitted on train only | PASS |
| Scaling effective parity (prod vectors in train envelope) | **FAIL** (100% of real production rows out of envelope) |
| Missing/unknown/NaN handling deterministic + safe | PASS (deterministic; NaN/−inf rejected at boundary; +inf deterministic with domain escalation; malformed types degrade) |
| Feature ordering safety | PASS (explicit-name mapping; reorder → identical) |
| **OVERALL** | **FAIL** |

The two features that DO match (`hour_cos`, `is_business_hours`) are exactly the
two derived purely from the event's own clock time. Everything the training
pipeline derived from the IBM dataset's domain (amounts in dollars, chip/online
flags, MCC/zip/state, whole-history merchant behavior) was either re-derived from
different PS-14 proxies at different scales, aliased to unrelated quantities
(`merch_tx_count` → known-device count; `chip`/`is_online` → new-device flag), or
hardcoded to zero. This is the mechanism behind the check #16/#21 finding that
the deployed decision layer is inert (calibrated scores saturate ≤ 0.254, every
SHAP explanation dominated by constant features): **matching column names between
the offline cache and the runtime mapper are not the same features.**
