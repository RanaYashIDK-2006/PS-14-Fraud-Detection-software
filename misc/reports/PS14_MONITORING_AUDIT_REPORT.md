# PS-14 — Check #29: Model Monitoring & Post-Deployment Drift Audit

**MONITORING VERDICT: FAIL** — the *monitoring components* exist and, when built
into a harness and tested by injection, behave as designed (drift → CRITICAL →
rules-only fallback). But **no monitoring is operationally armed today**: the
runtime drift detector in the served risk service is a no-op because it loads a
baseline from `models/data/drift_baseline.json`, which does not exist — while the
only recorded baseline (`data/drift_baseline.json`) lives in a path the service
never reads. On top of that, the recorded baseline is blind to the domain's own
attack flags, the stored live population is already "critically drifted" from it,
and no confirmed labels exist, so the delayed-label metrics the rubric demands
are not yet observable on live traffic.

Evidence: `reports/monitoring_audit.json` (generated by `scripts/monitoring_audit.py`,
~60 s; uses the real runtime `DriftDetector`, the real recorded baseline, DB-2/DB-3
rows, and the training-domain reference `data/transactions.csv`).

## 1. Monitoring-wiring audit — the deployment is unarmed

| Path | State |
| ---- | ----- |
| Runtime detector baseline (`models/data/drift_baseline.json`) | **missing** (no `models/data/` dir) → `DriftDetector(baseline_path=missing)` is a documented no-op passthrough on every request |
| Only existing baseline (`data/drift_baseline.json`) | exists — n=9,759 events, dated **2025-06→12**, built 2026-08-16, §16 features |
| Result | The served risk service has **no drift fallback armed**: nothing can pause ML or raise `DRIFT_*` reason codes today |

## 2. Data-quality monitor (DB-2, 199 stored rows) — PASS on stored data, with gaps

- Missing values: **none** on any §16 feature; duplicates: **0**; invalid values
  (ratio < 0, hour ∉ [0,23], non-binary flags): **0**; schema columns all present.
- Gaps (structural, not fixable from the store): no persisted "known token at
  deploy" registry → **novel device/location/recipient rate is not computable
  retrospectively** (must snapshot at first boot); no source timestamp on DB-2 →
  real-time ingest lag **UNVERIFIED** from the store alone.

## 3. Feature drift — reference mismatch dominates

Live DB-2 rows vs the recorded baseline (`data/drift_baseline.json`):
**max PSI 14.09 — CRITICAL by a factor of 56× the 0.25 alert band**, driven by
`hour_of_day` 14.09, `days_since_last_similar_txn` 13.11, `known_device_count`
11.46, `txn_freq_last_24h` 4.86. Interpretation matters: the stored rows are
from a different demo era (hour frozen at 12, tenure 0), so part of this is
era/domain mismatch — which is exactly the point: **an armed detector against
the only recorded reference would have paused ML on the current stored
population**, and there is no reference aligned to the currently deployed
model's training distribution (that distribution itself is unverified —
checks #16/#21/#27).

A runtime-format baseline was also built from DB-2 and found unusable: the
199-row corpus is degenerate — every §16 feature except `amount_ratio` is
constant, so a DB-2-built reference measures almost nothing.

## 4. Injection tests — the detector works when given a real reference

Baseline = the training-domain reference (`data/transactions.csv`, 200 K rows),
the domain the runtime serves. Real `DriftDetector`, real PSI, real thresholds:

| Test | Result | Evidence |
| ---- | ------ | -------- |
| Normal stream (420 domain rows) | **normal** | max PSI 0.031, no fallback |
| Structural drift (night hours, ratio 8–60, auth failures) | **CRITICAL + fallback** | PSI 0.25 → 0.85 → 1.77; `should_fallback=True` |
| 100% missing (all-keys-absent → 0-fill) | critical — but **incidentally** | PSI 14.9 only because 0 falls outside reference bins (days-since etc.) |
| **Attack wave on attack flags** (normal rows + `new_device=1`, `unusual_location=1`, `failed_auth=5`, mule-ring 0.9) | **INVISIBLE — state NORMAL, PSI 0.04** | the reference marks those 7 features CONSTANT, and PSI skips constant features. The generator produced zero variance on them, so the reference is blind to the domain's own ATO/mule signals |
| Live legacy DB-2 rows vs training reference | CRITICAL | PSI 13.9 — see §3 |

The blind-spot result is the most important monitoring design finding: an attack
wave that only moves `new_device_flag`/`unusual_location_flag`/
`failed_auth_count_24h`/`known_device_count`/mule-ring counts — the account
takeover signature — reads **NORMAL** because those features never vary in the
training reference. A DQ/categorical channel (per-flag rate against a small
alert threshold) is required alongside PSI.

## 5. Score drift & alert volume (DB-3, 574 real scores)

- `risk_score`: mean 10.7, median 1, p90 16, p99 80, max 80.
- High-band decisions: **7.0% (40/574) vs the <1% FPR budget** → alert-volume
  WARNING on this era (rows predate the current artifacts; band-highs arise from
  rule/velocity/limit triggers, not the 85+ band — `%≥85` = **0.0%**).
- ML threshold monitor: `%ml ≥ 0.007` (recall-gate point) = **100%** — the
  deployed calibrated scores saturate above it (cross-model calibrator,
  check #21), so enabling the recall gate would flag every transaction.
- Per-hour alert rates vary 0–25% across the day — a monitoring table the
  threshold monitor should keep per window.

## 6. Delayed-label monitor — designed and capability-tested; live metrics NOT-YET-OBSERVABLE

- **Observed:** 0 confirmed outcomes (`verification_outcomes` empty; no label
  column on `risk_scores`). Live precision/recall/FPR/PR-AUC/calibration are
  **not-yet-observable** — labels only exist after human verification, and none
  has happened in the local stores.
- **Capability test** (2,000 simulated §16 rows, independent label model, 7-day
  horizon — 1,513 observed after horizon, 487 pending): the metric pipeline
  runs (ROC-AUC 0.588, PR-AUC 0.318 on the *deployed calibrated scores* — i.e.,
  the deployed model does not rank this simulated PS-14 attack stream; a
  separate model-behavior finding, not a monitor failure). The horizon
  separation (observed vs pending) works as designed.

## 7. Segment monitor — capability on simulated batch; real join blocked

DB-2 (199 features rows) and DB-3 (574 score rows) are separate stores from
different eras with no shared join window in local state, so segment × score is
not computable on real data. On the simulated labeled batch, segment metrics
compute correctly and separate the populations (night 0–3 fraud rate 0.36 vs
day 0.19; new-device 0.42 vs known 0.15; high-amount 0.42; combo 0.66) — the
segment monitor itself works; the store split blocks the live version.

## 8. Monitoring failure / staleness — guard built and proven

The raw detector reports `state=normal` with 1 event and no recent traffic —
**monitoring must not report healthy from silence**. A freshness guard was
implemented and tested: `<30 events` or `>24 h` since last data →
**UNKNOWN/not healthy** (never HEALTHY). This wrapper is the required fix for
the "healthy while data stopped" failure mode.

## Verdict

**MONITORING VERDICT: FAIL** — for production operation, not for component
existence. Tested true: the PSI detector flips normal → CRITICAL → rules-only
fallback on structural drift when given a real reference; staleness can be
guarded so silence never reads healthy; the delayed-label metric pipeline and
segment monitor compute correctly. Tested false / not operational: the served
service runs the detector with **no baseline (no-op)**; the only recorded
reference is stale-era and **blind to the domain's attack flags**; the stored
live population already measures CRITICAL against it; and live delayed-label
metrics are not yet observable (0 confirmed labels). Until the baseline path is
wired to a reference derived from the *deployed* model's training data — itself
unverified (checks #16/#21/#27) — the monitoring layer cannot be trusted to say
"healthy", and its blind spot on new-device/mule-ring waves means it cannot see
the fraud patterns PS-14 exists to catch.
