## 9. CI enforcement

        run: python backend/scripts/claim_evidence_check.py

`backend/scripts/claim_evidence_check.py`:

1. **Registry integrity** — every `docs/evaluation/claims_registry.jsonl` entry must
   resolve: ledger records must exist with dataset sha + git + command (+ seed or an
   explicit `seed_not_applicable` reason for DEMONSTRATED), artifacts must contain the
   registered value within tolerance, suite evidence must contain its expected marker,
   `NOT ESTABLISHED`/`BLOCKED` entries must carry a reason/blocker instead of evidence.
2. **Surface coverage** — inside README managed regions
   (HTML comment markers delimited by `claims:managed:start` and `claims:managed:end`),
   every quantitative table row must carry a
   registered `<!-- claims:C-NNN -->` annotation whose registered value appears in the
   row. This is a structured claim registry + region mechanism, **not** a prose-wide
   regex sweep: formulas, versions, dates, code, prose and historical audit tables
   outside the regions are not scanned (documented limitation).

## 12. Limitations (nothing hidden)

1. **Enforcement surfaces are narrow by design:** only the README benchmark region and
   this report's historical-claims table are managed. Quantitative claims elsewhere in
   the README (claims-table test counts, prose numbers) are *not* yet machine-enforced;
   expanding surfaces is future work, not a completed guarantee.
2. External/IBM phase-era results (23B/24/25, ibm_train) are **traced, not re-executed**;
   their classifications rest on artifact inspection (DEMONSTRATED for 0.595 via
   provenance-complete artifact; SELF-TESTED where seed/git are absent).
3. **CI steps are locally verified only** — they have not run on the GitHub runner;
   they will also require the new evidence files (`reports/ulb_results.json`,
   `reports/phase105/*`, `reports/calibration_test/*`, the ledger update) to be
   committed together with the README, otherwise CI will (correctly) fail on missing
   evidence.
4. `fraud_report.py` success path untestable (missing producer-less artifacts).
5. Calibration metrics measure the **synthetic validation split** only; the 4 duplicate
   calibration records come from repeated identical executions (file-change hook
   verification runs) — preserved as append-only evidence.
6. `cross_dataset_eval.py` output overwrote the tracked Sep-13 report in place (its
   documented behavior); the historical content remains in git and the new content is
   value-identical (only timestamp + `command` differ).
